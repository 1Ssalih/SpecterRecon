### ASSISTANT
# SpecterRecon — Service Version Detection Refactoring Plan

Bu dokümanın amacı, SpecterRecon'un servis ve versiyon tespitinde yaşadığı problemleri tek bir uygulama planı halinde düzeltmektir. Bu plan, mevcut `banner.go` merkezli yapıyı daha güvenilir, daha az gürültülü ve daha yüksek doğruluklu bir **Service Version Detection Engine** haline getirmeyi hedefler.

Uygulama sırasında mümkünse mevcut public davranış bozulmamalı, ancak iç mimari aşağıdaki kurallara göre yeniden düzenlenmelidir.

---

## 1. Mevcut Durumdaki Temel Problemler

### 1.1 HTTP probe çok erken çalışıyor

Mevcut akışta `AnalyzeService` önce HTTP probe deniyor:

```go
httpRes := ProbeHTTPService(ip, port, isSSL, timeout)
```

Bu yaklaşım şu sorunlara yol açıyor:

- SSH, FTP, MySQL, PostgreSQL, SMTP gibi servisler HTTP isteği beklemiyor.
- HTTP isteği gönderildiğinde servis bağlantıyı kapatabiliyor veya anlamsız cevap verebiliyor.
- Servisin gerçek banner'ı henüz okunmadan bağlantı "kirletiliyor".
- Özellikle SSH gibi önce banner gönderen servislerde versiyon tespiti başarısız olabiliyor.

### 1.2 Raw socket okuması tek seferlik ve küçük

Mevcut yapıda genellikle:

```go
buf := make([]byte, 1024)
n, _ := reader.Read(buf)
```

şeklinde tek okuma yapılıyor.

Bu nedenle:

- 1024 byte üzerindeki banner'lar kesiliyor.
- Multi-line FTP banner'ları eksik yakalanıyor.
- Bazı servisler banner'ı birden fazla TCP segmentinde gönderdiği için versiyon satırı kaçırılabiliyor.
- Yavaş servisler timeout nedeniyle tamamen boş dönebiliyor.

### 1.3 Probe seti çok sınırlı

Mevcut yapıda sadece bazı portlara özel probe var:

- SMTP için `EHLO`
- FTP için `SYST`
- Redis için `INFO`
- Diğerleri için genellikle `\r\n\r\n`

Eksik kalan kritik servisler:

| Servis | Port | Beklenen Yaklaşım |
|---|---:|---|
| SSH | 22 | Önce banner dinle, gerekirse SSH client banner gönder |
| MySQL | 3306 | İlk handshake packet parse edilmeli |
| PostgreSQL | 5432 | SSLRequest veya startup probe |
| Memcached | 11211 | `version\r\n` |
| MongoDB | 27017 | Binary hello/isMaster |
| SIP | 5060 | `OPTIONS` |
| RDP | 3389 | TPKT/X.224 connection request |
| IMAP | 143 | Banner okuma + capability |
| POP3 | 110 | Banner okuma + capability |
| LDAP | 389 | Hafif LDAP probe |

### 1.4 Regex kuralları kırılgan ve önceliksiz

`ExtractVersionFromText` mevcut haliyle regex kurallarını sırayla geziyor ve ilk eşleşmeyi kabul ediyor.

Bu şu sorunları doğuruyor:

- Yanlış servis eşleşmesi olabilir.
- Genel bir regex, daha spesifik bir servisin önüne geçebilir.
- Versiyon extraction bazı banner formatlarında başarısız olabilir.
- Aynı banner içinde birden fazla teknoloji varsa doğru seçim yapılamaz.

Örnek:

```text
Apache/2.4.41 (Ubuntu) OpenSSL/1.1.1f
```

Burada sadece Apache versiyonu mu, OpenSSL versiyonu mu, yoksa Ubuntu bilgisi mi öncelikli olacak net değil.

### 1.5 SSL/TLS servislerinde versiyon ve teknoloji tespiti zayıf

HTTPS portlarında sadece HTTP header'ına bakmak yeterli değil.

Eksikler:

- TLS sertifika bilgileri toplanmıyor.
- Certificate Subject/Issuer üzerinden teknoloji çıkarımı yapılmıyor.
- TLS version ve cipher suite bilgisi servis tespiti için kullanılmıyor.
- SNI davranışı test edilmiyor.

### 1.6 Versiyon tespitinde confidence yok

Mevcut yapıda bulunan versiyonun ne kadar güvenilir olduğu bilinmiyor.

Örneğin:

- `Server: nginx` header'ı geldi ama versiyon yok.
- Banner içinde `OpenSSH_8.9` bulundu.
- HTML title içinde `Jenkins` geçti.

Bunların hepsi aynı ağırlıkta değerlendirilmemeli.

## 2. Hedef Mimari

Yeni servis tespit motoru aşağıdaki prensiplerle çalışmalı:

1. Önce pasif banner toplanır.
2. Servis tipine göre güvenli ve minimal probe gönderilir.
3. Gelen cevap binary veya text olarak parse edilir.
4. Birden fazla kanıttan confidence score üretilir.
5. HTTP probe sadece HTTP/HTTPS olma ihtimali yüksek portlarda veya raw aşama başarısız olduğunda çalışır.
6. SSL/TLS servislerinde sertifika ve TLS metadata da delil olarak kullanılır.
7. Bulunan sonuçlar `VersionSource`, `VersionConfidence`, `Evidence`, `ProbeUsed` alanlarıyla zenginleştirilir.

## 7. Yeni Raw Banner Okuma Fonksiyonu

Mevcut `GrabRawSocketBanner` fonksiyonu aşağıdaki davranışlarla yeniden yazılmalıdır.

Yeni fonksiyon adı önerisi:

```go
func GrabServiceBanner(ip string, port int, timeout time.Duration) ProbeResult
```

Davranış:

1. TCP bağlantısı kurulur.
2. Önce `ReadFirst` true olan servisler için hiçbir şey göndermeden banner beklenir.
3. Buffer size en az `8192` olmalıdır.
4. En az `maxReads` kadar okuma denemesi yapılır.
5. Her okuma `read_timeout_ms` kadar bekler.
6. Toplam süre `timeout_ms` değerini aşmamalıdır.
7. Okunan tüm byte'lar birleştirilir.
8. Önce binary parser çalışır.
9. Binary parser sonucu yoksa text sanitize edilir.
10. Match rules çalıştırılır.
11. En yüksek confidence'lı sonuç seçilir.
12. Hiçbir sonuç yoksa raw banner evidence olarak saklanır.

Örnek mantık:

```go
func GrabServiceBanner(ip string, port int, timeout time.Duration) ProbeResult {
    addr := net.JoinHostPort(ip, strconv.Itoa(port))

    conn, err := net.DialTimeout("tcp", addr, timeout)
    if err != nil {
        return ProbeResult{}
    }
    defer conn.Close()

    spec := FindProbeSpecByPort(port)

    var allData []byte
    buf := make([]byte, 8192)

    if spec.ReadFirst {
        for i := 0; i < spec.MaxReads; i++ {
            conn.SetReadDeadline(time.Now().Add(1500 * time.Millisecond))
            n, err := conn.Read(buf)
            if n > 0 {
                allData = append(allData, buf[:n]...)
            }
            if err != nil || n == 0 {
                break
            }
        }
    }

    if len(allData) == 0 && len(spec.InitialProbe) > 0 {
        conn.SetWriteDeadline(time.Now().Add(1000 * time.Millisecond))
        conn.Write(spec.InitialProbe)

        for i := 0; i < spec.MaxReads; i++ {
            conn.SetReadDeadline(time.Now().Add(1500 * time.Millisecond))
            n, err := conn.Read(buf)
            if n > 0 {
                allData = append(allData, buf[:n]...)
            }
            if err != nil || n == 0 {
                break
            }
        }
    }

    if len(allData) == 0 {
        return ProbeResult{}
    }

    if spec.BinaryParser != nil {
        if res, ok := spec.BinaryParser(port, allData); ok {
            return res
        }
    }

    text := SanitizeBanner(string(allData))

    return MatchBannerAgainstRules(spec, text)
}
```

## 8. HTTP Probe Ne Zaman Çalışmalı?

HTTP probe aşağıdaki koşullarda çalışmalıdır:

1. Raw probe sonucu kesin bir servis/versiyon üretmediyse.
2. Port bilinen HTTP portlarından biriyse.
3. Port config içinde `http_fallback_ports` listesindeyse.
4. Raw cevap `HTTP/1.`, `HTTP/2`, `<html`, `Server:`, `Location:` gibi HTTP izleri içeriyorsa.

Önemli kural:

SSH, FTP, MySQL, PostgreSQL, Redis, Memcached gibi servisler tespit edildiyse HTTP probe çalıştırılmamalıdır.

## 9. Yeni AnalyzeService Akışı

`AnalyzeService` fonksiyonu aşağıdaki sırayla çalışmalıdır.

```go
func AnalyzeService(portInfo core.PortInfo, timeout time.Duration) core.ServiceDetail {
    ip := portInfo.IP
    port := portInfo.Port

    // 1. Raw service probe ve banner collection
    probeRes := GrabServiceBanner(ip, port, timeout)

    // 2. Eğer raw probe kesin sonuç verdiyse direkt dön
    if probeRes.ServiceName != "" && probeRes.Confidence >= 80 {
        return buildServiceDetailFromProbe(probeRes, portInfo)
    }

    // 3. TLS/SSL ihtimali varsa TLS probe yap
    if isLikelyTLSPort(port) || probeRes.ServiceName == "" {
        sslRes := ProbeTLSService(ip, port, timeout)
        if sslRes != nil {
            probeRes.SSLInfo = sslRes
            probeRes.Evidence = append(probeRes.Evidence, VersionEvidence{
                Source:     "tls",
                Detail:     sslRes.Subject,
                Confidence: 30,
            })
        }
    }

    // 4. HTTP ihtimali varsa HTTP probe yap
    if shouldTryHTTP(port, probeRes) {
        httpRes := ProbeHTTPService(ip, port, isLikelyTLSPort(port), timeout)
        if httpRes.IsHTTP {
            return mergeHTTPResultWithProbe(probeRes, httpRes, portInfo)
        }
    }

    // 5. Hala servis bulunamadıysa düşük confidence ile raw banner döndür
    return buildUnknownServiceDetail(probeRes, portInfo)
}
```

## 10. Confidence Scoring Sistemi

Versiyon tespiti için confidence score kullanılmalıdır.

Önerilen puanlar:

| Kanak | Confidence |
|---|---:|
| Binary protocol parser ile MySQL/MariaDB version | 95 |
| SSH banner içinde OpenSSH version | 95 |
| Redis `redis_version` | 95 |
| Memcached `VERSION` | 95 |
| FTP banner içinde vsftpd/ProFTPD version | 90 |
| HTTP `Server` header içinde net version | 85 |
| HTTP `X-Powered-By` içinde PHP/ASP.NET version | 80 |
| SMTP EHLO içinde ürün adı | 75 |
| TLS certificate subject/issuer hints | 30 |
| HTML title üzerinden teknoloji tahmini | 20 |
| Raw banner içinde sadece ürün adı | 60 |
| Raw banner içinde versiyon benzeri string | 70 |

Aynı servis için birden fazla kanıt varsa confidence artırılabilir ama 100'ü geçmemelidir.

Örnek:

```go
func CombineConfidence(values []int) int {
    if len(values) == 0 {
        return 0
    }

    max := 0
    for _, v := range values {
        if v > max {
            max = v
        }
    }

    bonus := (len(values) - 1) * 5
    final := max + bonus
    if final > 100 {
        final = 100
    }

    return final
}
```

## 11. Regex Rule Sistemi Yeniden Düzenlenmeli

`ExtractVersionFromText` basit ilk-eşleşme mantığından çıkarılmalıdır.

Yeni kural yapısı:

```go
type ServiceRegexRule struct {
    Pattern     *regexp.Regexp
    ServiceName string
    Description string
    VersionExpr string
    Priority    int
    Confidence  int
}
```

Davranış:

1. Tüm kurallar çalıştırılır.
2. Eşleşen tüm sonuçlar toplanır.
3. Önce `Priority` değeri düşük olan kazanır.
4. Priority eşitse `Confidence` yüksek olan kazanır.
5. Hala eşitlik varsa daha uzun ve daha spesifik match kazanır.

Örnek rule:

```go

        Confidence:  95,

    {
        Pattern:     regexp.MustCompile(`vsftpd[\s/]?([\d.]+)`),
        ServiceName: "ftp",
        Description: "vsftpd",
        VersionExpr: `$1`,
        Priority:    1,
        Confidence:  90,
    },
    {
        Pattern:     regexp.MustCompile(`Apache[/\s]([\d.]+)`),
        ServiceName: "http",
        Description: "Apache",
        VersionExpr: `$1`,
        Priority:    10,
        Confidence:  85,
    },
    {
```

## 13. TLS/SSL Probe Modülü

Yeni fonksiyon önerisi:

```go
func ProbeTLSService(ip string, port int, timeout time.Duration) *core.SSLServiceInfo
```

Yapması gerekenler:

1. TLS handshake yap.
2. `InsecureSkipVerify: true` kullan.
3. Peer certificates topla.
4. TLS version ve cipher suite bilgisini al.
5. Subject, Issuer, DNSNames, NotBefore, NotAfter çıkar.
6. Certificate hints üret.

Örnek hint kuralları:

```go
Issuer contains "Let's Encrypt" -> "letsencrypt"
Subject contains "IIS" -> "iis"
Issuer contains "Microsoft" -> "microsoft"
Subject contains "localhost" -> "self-signed-likely"
DNSNames contains "*.azure" -> "azure"
```

Bu bilgiler doğrudan versiyon vermese de teknoloji tespitini güçlendirir.

## 14. Sanitization ve Binary Güvenliği

Banner parse sırasında binary veri kontrollü işlenmelidir.

Kurallar:

1. `SanitizeBanner` kontrol karakterlerini temizlemeye devam etmelidir.
2. Binary parser'lar panic yaşamamalıdır.
3. Slice index işlemleri length kontrolü yapmalıdır.
4. Null byte sonrası string parse edilirken boundary kontrol edilmelidir.
5. MySQL handshake parse sırasında packet length doğrulanmalıdır.
6. Max banner storage 64KB ile sınırlandırılmalıdır.

Örnek:

```go
const MaxBannerSize = 65536

if len(allData) > MaxBannerSize {
    allData = allData[:MaxBannerSize]
}
```

### 18.7 Performans ve stabilite

- Herhangi bir port timeout durumunda panic olmamalı.
- Boş banner durumunda uygulama crash olmamalı.
- Binary veri geldiğinde parser güvenli şekilde return etmeli.
- Tek bir port için toplam bekleme süresi config'deki timeout değerlerini aşmamalı.
- Tarama sırasında goroutine leak oluşmamalı.

## 20. Sonuç

Bu refactor ile SpecterRecon'un servis versiyon tespiti şu davranıştan:

```text
Önce HTTP dene, olmadı raw socket'e bak, tek okuma yap, ilk regex'e güven.
```

şu davranışa geçmelidir:

```text
Önce servis davranışını dinle, port bazlı doğru probe kullan, çoklu okuma yap,
binary/text cevapları ayrıştır, kanıtları topla, confidence üret,
HTTP'yi yalnızca gerekli olduğunda fallback olarak kullan.
```

Bu yaklaşım hem daha doğru versiyon tespiti sağlar hem de hedef sistemlere gönderilen gereksiz veya yanlış protokol trafiğini azaltır.
